# M4/M5 参考案例复核契约

更新日期：2026-08-22

## 为什么要分层

当前仓库中的紫微和六爻单元测试是工程回归测试：它们能证明输入、序列化、版本和既定算法没有意外变化，但不能证明同一算法符合独立参考资料。因此，工程回归案例不能直接计入“人工/参考盘黄金案例”。

首版继续把两类证据分开：

| 类别 | 能证明什么 | 能否计入黄金案例 |
| --- | --- | --- |
| 工程回归 | 代码在固定输入下保持既定输出、边界和审计行为 | 否 |
| 独立参考 | 输入、版本、流派和外部结果均可定位，并经过人工复核 | 是 |

## 参考案例必填字段

每个候选案例在进入黄金集前必须记录：

- 稳定案例 ID、术数系统、规则集和版本；
- 不含真实用户隐私的输入，或已取得明确授权的脱敏输入；
- 来源等级、书名/实现名、版次或固定版本、卷章/页面/提交号等精确定位；
- 外部期望结果，以及逐字段的差异说明；
- 复核人、复核日期、复核结论和无法确定的流派差异；
- 若来源是开源实现，必须注明它只用于交叉验证，不把 S3 资料升级成传统规则权威。

代码契约位于 `packages/domain/src/reference-cases.ts`：紫微和六爻输入分别通过对应 schema，案例状态、来源、断言和隐私标记会在导入时校验；`reviewed` 没有复核记录、案例 ID 重复或包含个人资料时会被拒绝。统计只计算 `status: reviewed` 的案例。

## 关闭条件

M4 需要至少 100 个独立参考盘，覆盖闰月、子时、四化、亮度和主要运限；M5 需要至少 100 个有出处或人工复核的案例，覆盖静卦、独发、多动、旬空、冲合和变卦。每个案例先以 `candidate` 状态进入，完成逐字段复核后才改为 `reviewed`；存在未解释差异时必须保留为 `rejected` 或 `needs-review`，不能为了通过率删除。

在这些案例完成前，产品可以继续作为首版可复算工具发布，但不能宣称 M4/M5 已达到黄金集验收，也不能开启更丰富的解释性规则。
